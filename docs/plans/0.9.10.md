# Plan for v0.9.10: isolation, events, modes and access

The second stage of [the Preparation Framework](0.9.9.md), staged by the owner on 2026-11-11 ([the audit](audit-0.9.9.md#how-the-work-is-staged)). It builds on v0.9.9's recording and recovery, and is published and deployable on its own. The specification's rules of the work and its exit criteria hold unchanged ([v0.9.9's plan](0.9.9.md#the-rules-of-the-work)).

## First: the account-data test

Before the first migration, a CI test that loads a representative account (a library by edition and finish, decks with revisions, the token and progress ledgers, quests, achievements, campaign progress, auctions, sleeves), runs every migration, and compares the account's totals before and after ([the audit](audit-0.9.9.md#migrations-and-rollback)).

## Bot containment and game isolation (spec §6)

**The owner's choice: a process per game.** Each game runs in its own JVM beside the engine's front process, which keeps the routes, the card database's catalog and the registry, and forwards a game's requests to its process.

- **Moving a game.** A game's process is started with its recording; recovery is how a game crosses into it, and how it comes back when its process dies. The process's death is a recovery of that game alone.
- **Memory.** Each process has its own heap, sized by format (a duel's, a Commander table's, a six-seat court's), so a game that runs out of memory ends its own process and nothing else, and is taken up again (and given up after five fruitless recoveries, as since v0.9.9).
- **Admission.** The front process admits a game only when the memory its format needs is free, and refuses with a reason a player understands ("The tables are full; try again in a minute"), as the API's 429 does today.
- **Metrics.** Decision time, searches cut off, legal fallbacks, heap pressure and process failures, per game and in all, on the service route beside the recordings' numbers.
- **The unknown.** A JVM per game costs its own start and its own card classes: measured first, with the card database shared read-only. If the start is too slow, a pool of warm processes.
- **Done when** stress tests on complex Commander boards and six-seat King's Table show the bounds hold, a game killed on purpose leaves the others running, a full engine refuses in words, and a low-skill bot still plays differently from a bot out of budget.

## Structured game events and perspectives (spec §7)

As [the audit](audit-0.9.9.md#design-decisions) decided: events made from XMage's `GameEvent`s on the game thread, numbered in the game's sequence, written beside the recording's journal and kept by the API past the game; objects named by the views' stable ids; each event with its visibility; one perspective filter for seat, teammate, spectator and replay; SysOp's inspection apart. A developer's timeline viewer reads them. Measured first: how much cause XMage's events carry.

## Game modes and reward eligibility (spec §10)

A `mode` on every game, set at creation and filled for old games from what they are. One function decides what a mode and a seat may earn, with reason codes; `economy`, `progression`, `quests`, `awards`, `campaign` and `stats` ask it. A matrix test pins today's behaviour before anything moves, so nothing changes by default.

## Access, consent and temporary entitlement (spec §8)

One table of grants (grantor, subject, resource, scope, expiry, revocation, consent), audited, read where access is decided today and never copied into a game. Cross-account tests for each access type; a temporary card can reach neither a library nor the auction house.
