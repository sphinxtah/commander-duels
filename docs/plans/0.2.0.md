# Plan for v0.2.0: the next feature version

Prepared on 2026-10-20, when v0.1.1 was closed and deployed. The owner named the next version v0.2.0. Under the owner's numbering rule a minor version brings new features. This plan gathers what the scope asks for next, so the version can start from it; it proposes, and the decisions belong to the start of that thread. The authoritative scope is the owner's *Commander Duels Development Scope* (Revision 1.0, 2026-10-17; a Word document kept outside the repository). [The scope ledger](../backlog.md) lists every remaining gap, and requirement IDs below are the scope's.

## Where v0.1.1 left things

- **What can be played.** Practice games against bots, Legacy (one bot) and Commander (up to three bots), in the browser by mouse or keyboard, with card images cached from Scryfall ([the game screen](../game-screen.md)). Decks are the engine's fixed fixture decks; SysOp can also play deck lists of any card the engine implements.
- **Who can play.** Google sign-in with approval by SysOp, until the site opens to the public at v1.0.0 ([identity](../identity.md)).
- **The live site.** https://duels.thesphinx.co runs v0.1.1, with up to six games at once ([the live site](../deployment.md)). The repository is public: changes are pushed to GitHub, CI publishes images, and the owner deploys on the VM with `./update.sh`. A deploy still ends running games.
- **Quality.** A bug and security sweep found 54 defects, all fixed with tests ([v0.1.1](../releases/0.1.1.md)). The browser journeys play whole games against the real engine and check every WebSocket frame for concealed cards.

## Owner decisions that carry over

- **SysOp has full access.** It sees every hand and library (the audited inspection view), plays bots, and may use any card. Never propose limits on SysOp. Administrators and moderators keep the hidden-information limits (SEC05, NET14).
- **Sign-up.** Approval by SysOp until v1.0.0.
- **Every version deploys live.** The owner runs `./update.sh` on the VM, and I push to GitHub. Changes that need the live `.env` edited must say so in the release notes and give the command.
- **Hosting.** Hathor, the owner's homelab, behind the TSH nginx proxy. Nothing here mixes with any other environment's configuration.
- **Backups.** Nightly `pg_dump` on the VM, and the owner's Proxmox VE backups of the VM to the NAS.

## Candidate tracks

Each track is a version's worth of work on its own. A version should take one track and finish it to its exit evidence; the order below is the recommended one.

### A. Your own decks: the catalog and the deck builder (M1)

The scope's M1, "Catalog identity and decks", is the next unfinished milestone. Players can then play the practice table with their own decks instead of the fixture decks.

- **Catalog (CAT01–CAT10).**
  - Import Scryfall's bulk data: `oracle_cards` for gameplay records, `default_cards` for English printings, and rulings.
  - Give each card concept an internal ID, mapped to Scryfall's Oracle ID and to separate printing IDs (set, collector number as text, language, finish, layout, art).
  - Store faces explicitly (split, transform, modal double-faced, adventure, meld, tokens), color identity apart from colors, and structured costs.
  - Legality is a versioned decision per format and role.
  - Each card has a status: `catalog_only`, `mapped`, `implemented`, `certified`, `suspended` or `unsupported`, with the reason. A card is playable only when the engine implements it. Never unlock play from an import alone.
  - Imports stream, run as durable jobs with revisions, and a failed import leaves the last good catalog in use (T20).
  - Images come from the returned URLs through the bounded cache that v0.1.0 started.
- **Mapping to the engine.** XMage's own card database (93,992 printings, 32,739 names) is not a certified catalog. Each Scryfall concept maps to an XMage implementation or stays unsupported.
- **Decks (DECK01–DECK11).**
  - Create, rename, duplicate, archive, delete and restore decks. Revisions record the format, commander, main deck, sideboard, companion, printing choices, notes and a content hash. A game binds to an immutable revision.
  - Autosave drafts with visible state, and handle two tabs with optimistic concurrency.
  - A collection browser with filters, and a documented subset of Scryfall-like search parsed into parameterized queries.
  - Statistics: totals, mana curve and color sources.
  - Commander selection recalculates the legal pool and explains identity and partner errors.
  - The backend validates authoritatively, with structured errors (rule code, explanation, remedy).
  - Import and export plain-text lists and a versioned JSON format, with a preview and size limits. No URL import in the first delivery.
- **Exit evidence.** T03 (duplicate printings cannot bypass copy limits), T04 (Legacy deck sizes and sideboard), T05 (Commander count, identity, pairs and companion), T17–T20 (catalog revisions, unsupported and reprinted cards, failed imports), and realistic-catalog performance.
- **Depends on.** Nothing new. The worker's job system (leases, generations) exists and needs lease renewal and staged promotion for long imports.
- **Size.** Large. One version could do the catalog import with statuses plus a minimal deck builder (create, edit, validate, play in practice), leaving search syntax, statistics and guided creation (DECK04–DECK06) for later.

### B. Human opponents: tables and lobbies (part of M3, with NET from M2)

Two or more approved players at one table, Legacy or Commander, with bots filling the other seats.

- **Lobbies (NET02–NET03).** A lobby records the format and rules revision, seat count, human and bot seats, deck revisions, visibility and house rules. Changing settings clears readiness, and only the host changes them. Every seat is revalidated when ready and again atomically at match start, which freezes decks and settings.
- **Finding a table (NET01).** Start with invite-code private tables. Public queues, friends, presence and rematches come later.
- **Already done.** The engine plays any mix of humans and bots at two to four seats (v0.0.4). The API owns seat tokens and the controller lease (v0.0.6). The screen shows every seat's view (v0.1.0).
- **Also needed.**
  - Per-seat timers from server deadlines, and an abandonment policy (NET11–NET12).
  - Concede-game separated from leaving the table.
  - Spectators with an optional delay (NET14).
  - Chat (NET13) can wait.
- **Exit evidence.** T07 (four-human Commander, with an elimination and cleanup), T13 for every human and spectator payload, and T14 (resend after a disconnect).
- **Depends on.** Fixture decks are enough for a first cut, so Track A is not required. A deploy still ends games, which matters more once people play each other (Track C).
- **Size.** Medium to large.

### C. Games that survive a deploy: recovery journals (M2)

- **Recovery (NET08–NET10).**
  - Commit an action journal before acknowledging or broadcasting an action.
  - Fence old workers by generation.
  - Store periodic snapshots and a deterministic decision journal (RNG state, generated choices, timeout decisions).
  - Reconnect from the last acknowledged sequence, with exactly one controlling session.
- **The hard part.** XMage cannot be reproduced from a seed alone: it has random object IDs and a global RNG. The backlog's M0 item asks for a proof first: kill a worker, restart, and compare the state and views.
- **Exit evidence.** T14–T16, and deploy fixtures where a game continues after the API and engine restart.
- **Size.** Large, research first. A one-version spike with a go or no-go is the honest shape.

### D. Priority controls (the rest of UI07)

- **The scope (UI07).**
  - Pass priority, pass until a selected stop, hold priority, and full-control mode.
  - Stops for chosen phases and steps, and for responses to relevant actions.
  - Auto-yields that reset on documented events, and an emergency cancel.
  - Never use animation time as the response window.
- **Today.** Only "pass priority" with XMage's default stops. XMage's `HumanPlayer` has its own pass modes (to end of turn, until the stack resolves, to the next main phase), which the engine bridge does not expose yet.
- **Exit evidence.** T10 (nested spells and abilities, held priority, ordering, a cancelled payment, illegal targets), and browser journeys that use each mode.
- **Size.** Small to medium. It could join a smaller track in the same version.

### E. Fair bots: the AI hidden-information audit (AI02, AI05)

- **The problem.** XMage's "Computer - mad" AI searches a copy of the full game state, including every human's hand. The practice table says so in a notice.
- **The scope (AI02, AI05).** A bot gets only its seat's information. Simulations sample plausible hidden states. Each decision has a bounded budget with a valid fallback.
- **Exit evidence.** AI02 and AI05 evidence, T21 (bots answer every prompt family with only permitted information).
- **Size.** Large research. Changing XMage's AI is upstream code, so the engine image would need patches (`engine/xmage/patches`).

## Smaller items carried over

- **The log ahead of the board.** In CI run #30 a log line named a bot's card one view before the board showed it. The browser check allows it (the later-view rule), as the engine's does. A session was proposed on 2026-10-20 to find the remaining path, using run #30's artifact `browser-games-1`, which is kept until about 2026-11-03.
- **Named choices longer than 64 entries** (naming a card). This is the last request that pauses a game as `unsupported` (backlog P0, M0).
- **Engine dependency hygiene** (backlog P1). H2 1.4.197's CVEs (pinned upstream), JBoss Remoting, jsoup, a base image refresh, and a licence review: SEC06.
- **Edge cases left on purpose in v0.1.1.**
  - SysOp's guess lockout uses a lock inside the API process. It needs a database lock if the API ever runs several processes.
  - Three approved accounts can fill the 24-slot queue of new card-image lookups.
- **Engine log noise.** XMage logs "AI player thinks too long" for bots on large Commander boards (AI05 budgets).

## Recommendation

Take **Track A, scoped to a first deck builder**, for v0.2.0:
- import the Scryfall catalog with statuses and the mapping to XMage;
- create, edit and validate decks for Legacy and Commander;
- play them at the practice table.

It is the next milestone in the scope, every later track builds on deck revisions (lobbies bind them, and recovery records them), and it is the biggest change the owner and testers will notice. Track D could ride along if the version has room. Track B is the natural v0.3.0, and Track C a spike after it.

## Exit evidence (if Track A is chosen)

- A catalog import from Scryfall's bulk data, with each card's status, its mapping to an XMage implementation and the reason when it has none; a failed import leaves the previous catalog in use (T20).
- Deck creation and editing in the browser, with server-side validation for Legacy and Commander that explains every error (T03–T05).
- A practice game started with a player's own deck revision, which later edits do not change.
- Every new route's authorization tested; deck data never leaks between accounts (T29's deck case).
- The live site runs v0.2.0, and the live checks pass.
