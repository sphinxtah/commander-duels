# Plan for v0.1.1: fixes from going live

Prepared on 2026-10-19, when v0.1.0 closed. The owner named the next version v0.1.1. Under the owner's numbering rule a patch carries bug fixes, so this plan holds only the defects and rough edges found while building v0.1.0 and putting it live; new features belong to v0.2.0. It proposes; the decisions belong to the start of that thread. [The scope ledger](../backlog.md) remains the full list of work.

## Where v0.1.0 left things

- **The game screen.** Practice games against bots, Legacy and Commander up to four seats, played by mouse or keyboard, with card images cached from Scryfall and SysOp's inspection panel ([the game screen](../game-screen.md)).
- **The live site.** https://duels.thesphinx.co on `commanderduels`, behind the TSH proxy. CI publishes the images; `deploy/push.sh` deploys a tag ([the live site](../deployment.md)).
- **Evidence.** CI run #25, the live checks, and the owner's SysOp sign-in, game and Google sign-in ([release notes](../releases/0.1.0.md#verification)).

## Proposed work

1. **Sessions survive a rotation followed by an error.** When an account's roles change, its next request rotates the session. If that request then fails with an API error, FastAPI drops the new cookie, and the player is signed out.
   - **The fix.** Carry the rotated cookie on the request and add it to every response in one place, including error responses. Then remove the card-image routes' local workaround.
   - **The test.** A regression test on a route that fails right after a rotation.
   - **Source.** Found by the card-image work, and listed in the backlog.
2. **Wording that still says nothing is playable.**
   - **The Play page.** The formats section is still tagged "In development". The closing section still says "This first release establishes the application… gameplay will arrive".
   - **The release status in Settings.** It is labelled "Framework" and says the features listed "remain unavailable".
   - **The engine's health.** It still reports `gameplay_available: false`. Its documentation said it would turn true with a game interface.
3. **Tapped permanents overlap.** A tapped card turns sideways inside a slot sized for an upright card. It spills over its neighbours and the strip beneath it, which is visible in the 1920 and 1366 screenshots. The slot should take the turned card's footprint.
4. **A "Cast" that cannot be paid** (investigate first).
   - **What happened.** In CI run #24 the keyboard journey kept being offered a spell whose payment it could only cancel.
   - **What to establish.** Whether the engine's priority options include spells the seat cannot pay for: XMage's playable check against what a payment prompt then accepts.
   - **If so.** Hide them, or show them disabled with the reason (UI04). Either way a player must not reach a dead end.
5. **The log runs ahead of the board.**
   - **The cause.** The engine's seat snapshot pairs the view published at the last prompt with the log as it stands when the snapshot is sent. While the bots play, a line such as "Bot 2 casts Leatherback Baloth" can reach the browser before any view shows the spell. XMage writes it just before the spell reaches the stack.
   - **Why it is not a leak.** The card becomes public at once, and the engine's own checker allows exactly this.
   - **Why it still matters.** It confused the browser leak check in CI run #27, and a player can read about a move the board does not show yet.
   - **The fix.** Cap each snapshot's log at the entries that existed when its view was published, as spectator snapshots already are. The browser journeys' check then returns to "public in the same view".
6. **CI keeps the browser evidence.** When the browser games fail, upload `web/test-results`: screenshots, error contexts and the test player's last answers. Run #24 left nothing to inspect.
7. **Live operations:**
   - **Backups.** Confirm the first nightly backup ran (04:30), and rehearse a restore into a scratch database.
   - **The phone check.** Record that `/#sysop` shows the Play page from mobile data.
   - **Off-VM copies.** Decide where backups are copied off the VM.
8. **Tidying.** `web/public/brand/logo.webp` is no longer used since the banner replaced the hero logo. Remove it, or keep it for later with a note in [asset provenance](../asset-provenance.csv).

## Exit evidence

- A test shows that a role change followed by a failing request keeps the player signed in.
- The Play page, Settings and the engine's health describe playable practice games.
- Tapped permanents sit in their own footprint at 1920, 1366 and 390 px.
- Either a fixture reproduces the unpayable cast and the screen handles it, or a written finding shows the engine never offers one.
- A snapshot's log never names a move its view does not show yet.
- A failed browser journey in CI leaves its evidence as an artifact.
- The live site runs v0.1.1, the live checks pass again, and a backup restores.

## Not in v0.1.1 (candidates for v0.2.0)

- Human opponents, lobbies and matchmaking (NET02–NET03); recovery journals (NET08–NET09), so that a deploy no longer ends running games.
- The rest of UI07: passing to the end of turn, chosen stops and full control.
- The AI hidden-information audit (AI02).
- The M1 catalog: Scryfall imports and printing-exact images.
- More concurrent games on the larger VM (engine heap and `CD_ENGINE_MAX_GAMES`).

## Questions for the start of v0.1.1

1. **Scope.** Fixes only, as a patch? Or add one small feature, such as passing to the end of turn, and number it v0.2.0 instead?
2. **Unpayable casts, if confirmed.** Hide such options, or show them disabled with the reason?
3. **Backups off the VM.** Where to: the NAS, or another Proxmox storage?
4. **Capacity.** Keep two games and a 1.5 GB engine, or raise them now that the VM has 16 vCPU and 32 GB?
