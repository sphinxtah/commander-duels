# Plan for v0.0.6: authenticated game routing

> **Built on 2026-10-19.** The start of v0.0.6 accepted every recommended answer below: WebSocket now, Legacy and Commander, SysOp's any-card decks now, PostgreSQL now, and the port fix. SysOp's inspection covers any running game, not only its own, under the standing full-access decision. See [games through the API](../games.md) and [the release notes](../releases/0.0.6.md).

Prepared on 2026-10-19, when v0.0.5 closed, for the thread that opens v0.0.6. It proposes; the decisions belong to the start of that thread. [The scope ledger](../backlog.md) remains the full list of work, and [the v0.0.4 plan](0.0.4.md) the route to v0.1.0.

## Where v0.0.5 left things

- **Engine.** Human and bot seats at Legacy and Commander tables, typed prompts, per-seat and spectator views with leak checks. All of it is on development endpoints that scripts drive with raw seat tokens ([Commander tables](../engine/commander-tables.md)).
- **Identity.** Google sign-in, sessions with CSRF, roles, administration, the audit trail and SysOp ([identity](../identity.md)). SysOp holds `games.play`, `games.view_concealed` and `cards.any`; the features behind the last two do not exist yet.
- **Gap.** The API routes no game actions, and no account owns a seat. This is the last step before v0.1.0's testing UI.

## Goal

A signed-in player, SysOp in particular, starts a practice game against bots through the API, plays it, and sees only what the seat may see. The API, not the browser, holds the engine's seat tokens, and one browser tab at a time controls the seat. SysOp can also inspect every hand and library in its own games, to check how the bots play.

## Work

1. **Practice games through the API.**
   - `POST /api/v1/practice-games` creates a game with a format, the player's seat and bot seats, and a fixture deck.
   - The API calls the engine, keeps the seat tokens server-side, and records which account owns which seat.
   - The browser receives only a game ID.
2. **Commands and views.**
   - Answers go through the API with an action ID, the expected revision and the prompt ID. The API checks the session, the seat's owner and the schema, then forwards them with the seat token.
   - Views come back unchanged from the engine, so the leak rules stay where they are.
3. **Controller lease (AUTH07).**
   - One connection per seat may issue commands. Taking control from another tab rotates the lease and invalidates the old one.
   - Other tabs of the same account observe.
4. **Events (NET05–NET07).**
   - A WebSocket per game pushes view revisions and prompts. It is authenticated by the session cookie, never by a token in the URL.
   - Clients resynchronise by revision.
   - Resent commands run once (T14). Every payload passes the leak checks (T13).
5. **Engine boundary.**
   - Service authentication between the API and the engine, and a game API that is not the development flag.
   - Per-account and global game limits.
   - The development endpoints stay for scripts.
6. **SysOp's game powers.**
   - **Practice games against bots.**
   - **The inspection view.** It is a new, explicit engine view type that shows every hand and library in order, built field by field like the others. It is available only to SysOp and only for its own games, and every opening is audited.
   - **Test decks from any card the engine implements (`cards.any`).** This needs a deck-list input and a card-name lookup in XMage's database. It may wait for v0.1.0; see the questions.
7. **Tests and tooling.**
   - A scripted client that plays a whole game through the API as a signed-in account.
   - HTTP and WebSocket tests for ownership, lease takeover, resends and leaks.
   - The CI smoke runs one API-routed game.

## Exit evidence

- A Legacy game against a bot, played through the API by a signed-in account, finishes. Every payload passes the leak checks, and a second tab can watch but not command.
- A disconnect and resend leaves the action applied once (T14).
- Another account cannot read or command the game (T29's match case).
- SysOp's inspection view shows the bot's hand and library, matches XMage's state, and is audited.

## Not in v0.0.6

- The game interface (v0.1.0).
- Recovery and replay journals (NET08–09), the AI hidden-information audit (AI02), lobbies, matchmaking and the catalog.

## Questions for the start of v0.0.6

1. **Transport.** WebSocket events now, as the scope's protocol, or a simpler long-poll first and WebSocket with the UI?
2. **Formats.** Legacy against a bot only (the minimum v0.1.0 needs), or Commander tables with bots as well?
3. **SysOp's any-card decks.** In v0.0.6 (deck-list input and card lookup), or in v0.1.0 with the deck screen?
4. **Persistence.** Record games, participants and results in PostgreSQL now, or keep games in memory until the recovery work?
5. **Small fix.** Make PostgreSQL's host port configurable, so a Windows port reservation cannot block `docker compose up`?
