# Plan for v0.1.0: the testing interface and the live site

Prepared on 2026-10-19, when v0.0.6 closed, for the thread that opens the next version. It proposes; the decisions belong to the start of that thread. By the numbering rule, the first version with a testing interface you can use is v0.1.0. [The scope ledger](../backlog.md) remains the full list of work, and [the v0.0.4 plan](0.0.4.md) the route that ends here.

## Decisions at the start of v0.1.0

Agreed on 2026-10-19 at the start of the thread:
- **Formats on screen.** Legacy, and Commander up to four seats with the UI02 layout. The owner chose the larger build, not the recommended two-seat Commander.
- **Card faces.** Card images, not text frames alone (the owner's choice over the recommendation). The engine's views carry names only, so images are looked up by name from Scryfall. The API caches them on its own disk and serves them from the site itself (the owner chose this over loading them from Scryfall's CDN). A text frame from the engine's view stays underneath every image.
- **Who plays.** Approved players only, approved by SysOp. The live site uses approval sign-up until it opens to the public at v1.0.0. The game screen tells players that the bots read their hand (AI02).
- **Priority controls.** Pass priority with XMage's default stops (as recommended).
- **Live deployment** (a condition the owner set when v0.0.6 closed). v0.1.0 is official only once it runs live, and every later version deploys there.
  - **Host.** `duels.thesphinx.co`, on a new Debian 13 VM on Hathor, behind the owner's TSH nginx proxy (nginx with certbot on another VM). The A record points at the owner's public IP.
  - **Delivery.** CI builds the images and pushes them to GitHub's container registry; the VM pulls them. The owner preferred this to building on the VM.
  - **Who deploys.** The deploying computer, over SSH, with its own key.

The deployment is in [the live site](../deployment.md).

## Where v0.0.6 left things

- **Engine.** Legacy and Commander tables with typed prompts, authorized seat views, spectator views and leak checks ([Commander tables](../engine/commander-tables.md)).
- **Identity.** Google sign-in, sessions, roles, the audit trail and SysOp ([identity](../identity.md)).
- **Games through the API.** Practice games against bots and a WebSocket per game. The controller lease, resends that run once, SysOp's inspection view and any-card deck lists, all played by a scripted client ([games through the API](../games.md)).
- **Gap.** No screen plays a game. The browser has the shell, the profile, administration and the logo.

## Goal

A signed-in player opens Play, starts a practice game against a bot and plays it to the end in the browser, using only the mouse or only the keyboard. The browser shows every prompt the fixture decks reach, and nothing the seat may not see. This is milestone M0's exit evidence: a browser Legacy game against a bot with no concealed-state leaks. SysOp also sees its inspection panel and can start a game from a deck list.

## Work

1. **Starting a game.** The Play page offers a practice game: format, your fixture deck, bots and bot skill. SysOp also gets a deck-list box with card-name lookup. It lists your running and recent games, with resume and close.
2. **The game screen (UI01, UI03, UI05).** Built in React DOM, as the scope sets it for now, with PixiJS left for later effects.
   - **Layout.** Your hand, the battlefields, the stack panel (source, controller, targets, resolution order), life totals and zone counts. Graveyard, exile and command-zone browsers, and the game log.
   - **Sizes.** 1920 x 1080 first, usable at 1366 x 768, and readable on a phone without horizontal scrolling.
   - **Commander states,** if Commander is in scope.
3. **Prompts (UI04, UI08).** One component per prompt kind the engine types:
   - priority, mulligan, yes/no and targets;
   - mana payment, attackers, blockers and damage assignment;
   - modes, amounts, ability choice, trigger order, piles, choices and defenders.

   Click to select and click to target. Every option is reachable by keyboard. An option the engine does not offer is never shown as playable.
4. **The connection.**
   - The game uses v0.0.6's WebSocket as the scripted client does: hello with the CSRF token, the lease, commands with action IDs, resync by revision, and resend after a reconnect.
   - A second tab shows that another tab is playing and offers "Play here", which takes the lease.
5. **SysOp's panel.** The inspection view beside the board: every hand and library in order, refreshed with each revision. The page states that the opening is audited.
6. **The banner.** The owner added a third piece of artwork on 2026-10-19, after v0.0.6 closed: `commander.duels.banner.png` (1916 x 821), a warrior on a battlefield with the full logo on the right.
   - **Placement.** Proposed for the Play page's hero, with the copy over its dark left side; on a phone, cropped to the logo half.
   - **Making it.** `scripts/brand_assets.py` makes its web sizes, and [asset provenance](../asset-provenance.csv) records it, like the logos.
7. **Accessibility.** Reduced motion and larger text as elsewhere, visible focus, and screen-reader names for cards and options. Colour is never the only signal.
8. **Tests.** Browser journeys that play a Legacy game against the bot through the interface to the end. One checks every payload the page receives for concealed information (T13 in the browser), and one covers the second tab and a reconnect (T14).

9. **The live site** (added for the owner's condition):
   - **Production configuration.** `CD_ENVIRONMENT=production` refuses to start without HTTPS, Secure cookies, a generated database password, the service token, a Google client ID and trusted proxies, or with a SysOp network that covers every address. The engine's development routes are off.
   - **Packaging.** A production Compose file (images from the registry, no published ports but the web container's, which only the proxy may use) and a bootstrap for the VM. A deploy script backs up the database before migrating, and a nightly timer backs it up too.
   - **The proxy.** The nginx site file for the TSH proxy (TLS, the WebSocket, `X-Forwarded-For`), and certbot's command.
   - **CI.** CI publishes the images on every push to `main` and every version tag.

## Exit evidence

- A Legacy game against a bot, played to the end in the browser by mouse, and again by keyboard. Every prompt the fixture decks reach is answered on screen, and no payload carries concealed information.
- A second tab watches and cannot play until it takes control. A dropped connection resumes without repeating an action.
- SysOp's inspection panel matches the game, and a SysOp deck list starts a game.
- The screen is usable at 1920 x 1080, 1366 x 768 and 390 px wide.
- The site is live at https://duels.thesphinx.co, behind the TSH proxy, and the checks in [the live site](../deployment.md#checking-the-live-site) pass.

## Not in v0.1.0

- Human opponents, lobbies and matchmaking (NET02–NET03); recovery journals (NET08–NET09).
- The catalog, deck building and card images (M1).
- Configurable stops and timers (UI07, NET11–NET12) beyond passing priority, unless chosen below.
- Animation (UI09), sound, help and glossary (UI10–UI11), and gamepads (UI12).

## Questions for the start of v0.1.0

1. **Formats on screen.** Legacy only, the M0 exit evidence; or Legacy and Commander, with the four-seat layout of UI02 (a larger screen to build)?
2. **Card faces.** Text frames built from the engine's view (name, cost, type, rules, power and toughness) with original CSS; or card images, which need the catalog and provenance work of M1 first?
3. **Who may play.** The bots still see a full copy of the game, including your hand (AI02). Should every signed-in player see the game screen, with a notice, or only SysOp and administrators until the AI audit?
4. **Priority controls.** Pass priority and XMage's default stops only; or the first part of UI07 as well: pass until end of turn, and stops you choose?
