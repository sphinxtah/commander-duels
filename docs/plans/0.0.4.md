# Plan for v0.0.4 and the route to v0.1.0

Prepared on 2026-10-18, when v0.0.3 closed, for the thread that opens v0.0.4. It proposes; the decisions belong to the start of that thread. [The scope ledger](../backlog.md) remains the full list of work.

## Where v0.0.3 left things

- **Engine.** Human-versus-bot Legacy games through XMage's `HumanPlayer` work end to end:
  - every request the fixture decks produce is a typed prompt;
  - stale and forged answers are refused;
  - every view sent to the seat passes leak checks against XMage's state ([the human seat](../engine/human-seat.md)).
- **Development only.** It all runs on internal development endpoints, driven by scripts. There is no sign-in, FastAPI does not route game actions, and there is no game UI.
- **Version numbering.** Each thread stays on 0.0.x until a thread delivers a testing UI you can use; that thread is v0.1.0.

## Route to v0.1.0

v0.1.0 needs three things in place:
- a browser path to a seat;
- an identity the API trusts;
- a server-chosen seat.

The architecture forbids routing game actions without authentication, seat ownership and a controller lease. Two orders reach that point. Both end with the same v0.1.0.

**Recommended: engine first.** This finishes the M0 critical path while the bridge code is fresh.

| Version | Theme | Main requirements |
| --- | --- | --- |
| v0.0.4 | Multiplayer seat bridge: Commander for 2–4 seats, Two-Headed Giant feasibility | FMT01, FMT02, FMT08–10 (feasibility), NET07, RULE05; engine-level T07, T08, T13 |
| v0.0.5 | Identity foundation: sessions, roles, audit, the SysOp local administrator, Google sign-in | AUTH01–07, SEC05, T01, T02, T29 |
| v0.0.6 | Authenticated game routing: practice games through FastAPI, server-held seat tokens, controller lease, WebSocket events | AUTH07, NET05–07, NET10 (partial), T13, T14 |
| v0.1.0 | Testing UI: play a Legacy game against the bot in the browser (the M0 exit evidence) | UI01, UI04, UI05, UI08 (fixture prompts), PAR12 (basic) |

**Alternative: interface first.** Swap v0.0.4 and v0.0.5, then go straight to routing and the UI, and run the multiplayer bridge after v0.1.0. This reaches a usable screen one version sooner. The cost is the scope's critical path: engine adaptation and hidden-information correctness. Four-seat views and the Two-Headed Giant question would stay open longer, and they are the items most likely to change the design.

The other open M0 items are listed below with a suggested slot. None has to block v0.1.0.

| Item | Suggested slot |
| --- | --- |

| Decision journal, recovery and fencing proof (NET08–09, T15–16) | After v0.1.0, when there is a UI to reconnect |

## v0.0.4: multiplayer seat bridge

### Goal

The v0.0.3 bridge, generalized from one human seat to any mix of human and bot seats at a Commander table of two to four. Every seat gets its own token and its own authorized view, and leak checks prove that no seat sees another's hand or library.

### Work

1. **Commander game setup.**
   - XMage's `CommanderFreeForAll` (already built and on the classpath since v0.0.2) for three and four seats.
   - `CommanderDuel` for two seats, labelled with the scope's two-seat Commander profile, not Duel Commander (FMT02).
   - Decks validated with XMage's `mage.deck.Commander`.
   - Starting life 40, the London mulligan, and Commander's own free mulligan if XMage applies it.
2. **Commander fixture decks.**
   - Four 100-card decks with simple cards, one mono-colour commander each.
   - No card name shared between decks, so the name-based leak check stays meaningful.
   - Kept with the existing fixtures in `engine/decks`.
3. **Seats.**
   - `POST /v1/games` takes a format and a list of seats, each human or bot.
   - The response returns one seat token per human seat. Each token selects its seat; no field in a request does.
   - Each human seat has its own prompt state and revision stream. XMage asks one player at a time on the single game thread, so at most one prompt is open per game.
4. **Views.**
   - Opponents as a list.
   - The command zone, commander tax and commander damage per commander (FMT01).
   - Eliminated players.
   - Each player's colour identity.
   - The contract file gains these fields; every object stays closed.
5. **Prompts.** Type what four-seat play reaches:
   - choosing which opponent or planeswalker to attack (defender choice);
   - multiplayer targets;
   - the commander's "move to the command zone?" replacement;
   - any `CHOOSE_CHOICE` or ability choice the decks produce.

   Anything else stays `unsupported`, as in v0.0.3.
6. **Leak checks.**
   - Run every check for every human seat against every other seat's concealed zones.
   - Tables to cover: one human with three bots, two humans with two bots, and four humans (scripted).
   - Extend the HTTP tests so one seat's token cannot read another seat's view.
7. **Two-Headed Giant feasibility.**
   - XMage at the pinned commit has no Two-Headed Giant game type, only cards with that name. FMT08 needs shared turns, shared life (30), team construction, team poison and teammate information sharing.
   - Produce a written assessment of three options, with an estimate and a recommendation:
     - a game type built in the engine module on XMage's primitives;
     - an upstream change;
     - a scope decision.
   - No implementation is promised in v0.0.4.
8. **CI and tooling.**
   - The scripted client learns seat lists.
   - CI adds a four-seat smoke game with schema validation.

### Exit evidence

- Scripted Commander games at two, three and four seats, including mixed human and bot tables, finish with zero leak-check failures across every human seat's payloads.
- Commander tax and commander damage in the views match XMage's state.
- A one-line command plays a four-seat game and prints each seat's prompts.
- A Two-Headed Giant feasibility note with a recommendation.

### Not in v0.0.4

- Browser UI, sign-in and API routing.
- Recovery.
- AI02.
- Ranked play.
- Lobby and readiness flow (NET02–03).
- Commander rules-zero settings (FMT03–04).

### Questions for the start of v0.0.4

1. **Order.** Engine first (recommended) or interface first?
2. **Table sizes and seat mixes.** Which must pass: all of two, three and four seats, or four only?
3. **Fixture decks.** Should the four Commander decks be invented from simple cards, as the Legacy fixtures were, or do you have specific commanders in mind?
4. **Two-Headed Giant.** Is a feasibility note enough for v0.0.4, or do you want a first playable prototype attempted?

**Answered on 2026-10-18, at the start of v0.0.4:** every recommended option.
1. Engine first, so the route stays v0.0.5 identity, v0.0.6 routing and v0.1.0 testing UI.

## SysOp local administrator

Requested on 2026-10-18. A local administrator account named SysOp, modelled on the one in Kingdom Connect:
- It can sign in only from your production network.
- It has every root-level ability in the interface ("full god abilities").

How it fits the scope:
- **Sign-in.** The scope fixes identity as Google sign-in only, so a local account is a scope addition. The ledger now records it as accepted, under M1.
- **First administrator.** AUTH06 bootstraps the first administrator through explicit configuration. SysOp can be that configured bootstrap, if you want it to replace the separate setting.
- **Concealed information.** Two requirements forbid exposing concealed information from a running match. SEC05 rules out an unrestricted "view all live hands" panel; NET14 rules out disclosure to anyone. A literal "every ability" SysOp collides with both, so the answer to question 3 below decides which requirement gives way.

Suggested design, to confirm in the identity thread (v0.0.5 in the recommended order):
- **Separate login.** A login form that only accepts requests from configured networks (for example `CD_SYSOP_NETWORKS`, a CIDR list). Client addresses are trusted only through configured proxies (`CD_TRUSTED_PROXIES`), so a forwarded header cannot fake the network.
- **Credential.** A password hashed with Argon2id, set by a command-line bootstrap or a mounted secret, never through the interface. Optionally a TOTP second factor, with sign-in lockout and rate limits.
- **Permissions.** The SysOp role holds every administrative permission, and SysOp cannot be deleted, demoted or disabled through the interface.
- **Audit.** Every SysOp action writes an audit event with the source address.
- **Sessions.** Short idle and absolute session expiry.

Open questions:

1. **Network.** Which network counts as production, and what is its CIDR? The scope deploys Commander Duels to your personal homelab (the Hathor VM), not TLIT's Acadia, so this should be the homelab network.
2. **Kingdom Connect.** What should SysOp copy from it: a fixed username, a separate login page, behaviour when the network check fails?
3. **Concealed information.** Does "every ability" include seeing concealed information in live games? Options:
   - SysOp has every power except live hidden information. This fits SEC05 and NET14.
   - SysOp can switch on an audited inspection mode that players can see and that voids the game's results.
   - SysOp sees everything. This would mean accepting a change to SEC05 and NET14.
4. **Second factor.** Should SysOp require one even from the production network?
5. **Play.** Can SysOp also play, and if so, do its games count toward ratings and progression?
