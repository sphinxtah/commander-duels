# Scope and remaining work

The user requested v0.0.1 as the initial framework, the foundation before M0. v0.0.2 is the first slice of M0: the XMage engine builds from a pinned commit on Java 21 and plays internal bot-versus-bot Legacy games ([findings](engine/xmage-spike.md)). v0.0.3 adds a human seat through XMage's `HumanPlayer`, with typed prompts, stale-answer refusal and authorized per-seat views, on development engine endpoints driven by scripts ([the human seat](engine/human-seat.md)). v0.0.4 generalizes that bridge to Commander tables of two to four seats, any mix of humans and bots, with per-seat tokens, commander tax and damage in the views, every fixture prompt family typed, read-only spectator views, and leak checks for every human seat and the spectator ([Commander tables](engine/commander-tables.md)). v0.0.5 adds identity: Google sign-in, sessions, roles, an append-only audit trail, administration screens and SysOp, the local root account ([identity](identity.md)). v0.0.6 routes games through the API: practice games against bots over an authenticated WebSocket, seat ownership, the controller lease, resends that run once, and SysOp's inspection view and any-card deck lists ([games through the API](games.md)). v0.1.0 is the first version you can play: the game screen for practice games against bots, Legacy and Commander up to four seats, with card images from Scryfall cached by the API, SysOp's inspection panel, and browser journeys that play whole games ([the game screen](game-screen.md)). It is the first version live at https://duels.thesphinx.co ([the live site](deployment.md)); every later version deploys there. v0.1.1 carries the fixes found while going live and in a bug and security sweep after it ([the v0.1.1 plan](plans/0.1.1.md), [release notes](releases/0.1.1.md)). It is live, deployed from the now public repository with the VM's `./update.sh`. v0.2.0 brings the scope's M1: the card catalog, imported daily from Scryfall and mapped to the engine's implementations ([the card catalog](catalog.md)), and players' own decks, built, validated, shared and played at the practice table ([decks](decks.md)), with the rest of the priority controls ([the v0.2.0 plan](plans/0.2.0.md), [release notes](releases/0.2.0.md)). Next is v0.3.0, chosen by the owner: the game screen during play, made to look exactly like Magic Duels, with Commander and the site's own features added ([the v0.3.0 plan](plans/0.3.0.md)). v0.3.0 went live as the Magic Duels table ([release notes](releases/0.3.0.md)). v0.3.1, named by the owner, is the Planeswalker Alliance ([the Planeswalker Alliance](progression.md), [release notes](releases/0.3.1.md)): levels earned by wins that open the owner's 98 Planeswalker portraits as alliances, each bringing its cards into the player's library, with ten new starter decks, bots that no longer see their opponents' cards, and deck building from the player's own library except for administrators ([the v0.3.1 plan](plans/0.3.1.md)). v0.4.0 brings tokens earned by winning ([tokens](tokens.md)), human tables where players play each other ([human tables](tables.md)), Leng's card shop, which sells packs from Unlimited to the current set, priced from market prices and following real pull ratios ([the shop](shop.md)), and the Godlike tier's custom cards in play, from a private engine plugin ([the v0.4.0 plan](plans/0.4.0.md)). v0.4.1, named by the owner, gets the site ready for about 20 beta testers: public About, Privacy and Terms pages, bug reports with screenshots, counts of waiting approvals and reports, account deletion, and up to 64 games at once ([the v0.4.1 plan](plans/0.4.1.md)). Next is v0.4.2, named by the owner: fixes for what the owner and the testers find ([the v0.4.2 plan](plans/0.4.2.md)). Document content supplies requirements, not permission to claim investigations or product functionality have been completed.

These are unaccepted gaps, not deleted scope. The reference CSV seeds all 18 scope feature families as unresolved. The scenario example is a draft schema fixture and cannot be played. Since v0.2.0 the catalog is imported from Scryfall, and a card is certified when the engine's implementation of it passes automatic gates and matches the Oracle card's characteristics ([coverage](catalog.md#the-engines-implementation-list)). That is not the scope's signed parity matrix (M6): no card's behaviour has been play-tested against the rules.

Follow-up tickets should include requirement IDs, dependencies, acceptance fixtures, diagnostic telemetry, migration effects and documentation changes. Add durable result/outbox processing before granting any rewards. Add per-user authorization before exposing user-owned domain records. Never unlock play on the basis of an imported card or a successful engine health response: only certified cards play. The one accepted exception is SysOp's own test decks and deck lists: any card the engine implements, in SysOp's practice games only.
