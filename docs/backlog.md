# Scope and remaining work

The user requested v0.0.1 as the initial framework, the foundation before M0. v0.0.2 is the first slice of M0: the XMage engine builds from a pinned commit on Java 21 and plays internal bot-versus-bot Legacy games ([findings](engine/xmage-spike.md)). v0.0.3 adds a human seat through XMage's `HumanPlayer`, with typed prompts, stale-answer refusal and authorized per-seat views, on development engine endpoints driven by scripts ([the human seat](engine/human-seat.md)). v0.0.4 generalizes that bridge to Commander tables of two to four seats, any mix of humans and bots, with per-seat tokens, commander tax and damage in the views, every fixture prompt family typed, read-only spectator views, and leak checks for every human seat and the spectator ([Commander tables](engine/commander-tables.md)). v0.0.5 adds identity: Google sign-in, sessions, roles, an append-only audit trail, administration screens and SysOp, the local root account ([identity](identity.md)). v0.0.6 routes games through the API: practice games against bots over an authenticated WebSocket, seat ownership, the controller lease, resends that run once, and SysOp's inspection view and any-card deck lists ([games through the API](games.md)). v0.1.0 is the first version you can play: the game screen for practice games against bots, Legacy and Commander up to four seats, with card images from Scryfall cached by the API, SysOp's inspection panel, and browser journeys that play whole games ([the game screen](game-screen.md)). It is the first version live at https://duels.thesphinx.co ([the live site](deployment.md)); every later version deploys there. v0.1.1 carries the fixes found while going live and in a bug and security sweep after it ([the v0.1.1 plan](plans/0.1.1.md), [release notes](releases/0.1.1.md)). It is live, deployed from the now public repository with the VM's `./update.sh`. v0.2.0 brings the scope's M1: the card catalog, imported daily from Scryfall and mapped to the engine's implementations ([the card catalog](catalog.md)), and players' own decks, built, validated, shared and played at the practice table ([decks](decks.md)), with the rest of the priority controls ([the v0.2.0 plan](plans/0.2.0.md), [release notes](releases/0.2.0.md)). These are unaccepted gaps, not deleted scope. The reference CSV seeds all 18 scope feature families as unresolved. The scenario example is a draft schema fixture and cannot be played. Since v0.2.0 the catalog is imported from Scryfall, and a card is certified when the engine's implementation of it passes automatic gates and matches the Oracle card's characteristics ([coverage](catalog.md#the-engines-implementation-list)). That is not the scope's signed parity matrix (M6): no card's behaviour has been play-tested against the rules.

Follow-up tickets should include requirement IDs, dependencies, acceptance fixtures, diagnostic telemetry, migration effects and documentation changes. Add durable result/outbox processing before granting any rewards. Add per-user authorization before exposing user-owned domain records. Never unlock play on the basis of an imported card or a successful engine health response: only certified cards play. Until v0.4.5 the one accepted exception was SysOp's own test decks and deck lists, any card the engine implements; since then a card that is not certified is out of the game for everyone, SysOp included ([catalog](catalog.md#only-playable-cards-are-in-the-game-v045)).
