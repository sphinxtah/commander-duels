# Scope and remaining work

The user requested v0.0.1 as the initial framework, the foundation before M0. v0.0.2 is the first slice of M0: the XMage engine builds from a pinned commit on Java 21 and plays internal bot-versus-bot Legacy games ([findings](engine/xmage-spike.md)). v0.0.3 adds a human seat through XMage's `HumanPlayer`, with typed prompts, stale-answer refusal and authorized per-seat views, on development engine endpoints driven by scripts ([the human seat](engine/human-seat.md)). v0.0.4 generalizes that bridge to Commander tables of two to four seats, any mix of humans and bots, with per-seat tokens, commander tax and damage in the views, every fixture prompt family typed, read-only spectator views, and leak checks for every human seat and the spectator ([Commander tables](engine/commander-tables.md)). v0.0.5 adds identity: Google sign-in, sessions, roles, an append-only audit trail, administration screens and SysOp, the local root account ([identity](identity.md)). v0.0.6 routes games through the API: practice games against bots over an authenticated WebSocket, seat ownership, the controller lease, resends that run once, and SysOp's inspection view and any-card deck lists ([games through the API](games.md)). [The v0.0.4 plan](plans/0.0.4.md) sets out the route to v0.1.0, the first version with a testing UI, which comes next. Document content supplies requirements, not permission to claim investigations or product functionality have been completed.

These are unaccepted gaps, not deleted scope. The reference CSV seeds all 18 scope feature families as unresolved. The scenario example is a draft schema fixture and cannot be played. The engine's XMage card database (93,992 printings) is not a certified catalog: no Scryfall cards are imported, mapped or certified; a coverage percentage would be misleading before a catalog snapshot is selected.

Follow-up tickets should include requirement IDs, dependencies, acceptance fixtures, diagnostic telemetry, migration effects and documentation changes. Add durable result/outbox processing before granting any rewards. Add per-user authorization before exposing user-owned domain records. Never unlock play on the basis of an imported card or a successful engine health response. The one accepted exception is SysOp's own test decks: any card the engine implements, in SysOp's practice games only.
