# v0.1.1: fixes from going live

A patch. It fixes the defects found while putting v0.1.0 live, and those found by a bug and security sweep of the whole application once it was live. Nothing new is playable: practice games against bots run as in v0.1.0, and the Play page, Settings and the engine's health now say so. The work follows [the v0.1.1 plan](../plans/0.1.1.md). Behaviour is described where it lives: [identity](../identity.md), [games through the API](../games.md), [the game screen](../game-screen.md), [the human seat](../engine/human-seat.md) and [the live site](../deployment.md).

## Scope agreed for this version

Agreed on 2026-10-20 (details in [the plan](../plans/0.1.1.md#decisions-at-the-start-of-v011)): a patch with the sweep's fixes, plan items 1–8 and six games at once on the live site. Backups leave the VM through the owner's Proxmox VE backups to the NAS.

## Fixed

### Security

**Sign-in and accounts:**
- **Google sign-in failures.** A bot can no longer fill the audit trail. Every attempt with a live challenge spends it, and a made-up or spent challenge is refused unrecorded. After 10 recorded failures from one address in 15 minutes, further failures get 429 `too_many_attempts` and are not recorded.
- **Sign-in challenges.** Each is a database row kept for a day, so the web container lets each visitor address ask for 10 a minute, after a burst of 20.
- **SysOp's lockout.** Parallel guesses can no longer outrun it: attempts are checked one at a time. Wrong current passwords on the Profile page's password change count toward it. A password set from the console lifts every address's lockout, as its message says.
- **Administrators' grants.** Only SysOp can restore, deny, sign out or change the roles of a disabled or pending account that holds an administrator grant. The account list shows such dormant grants, so the row stays locked.
- **Email.** Moderators no longer see account email addresses or find accounts by them; only administrators do.
- **The audit log.** A player without a handle can no longer pass for the Site administrator or another player. `site-administrator` and its variants are reserved handles.
- **Search.** The account search treats `%`, `_` and `\` as written, and the audit filter ignores case on PostgreSQL too.
- **Stored text.** A NUL character in a display name, a status reason or a search is refused with 422, not a server error.

**Resource limits:**
- **The database pool.** One player's burst of requests can no longer stall the whole API. A request gives its pooled connection back before it waits on a lock, the engine or Scryfall.
- **Game connections.** An account may hold 4 connections to a game, and a game 8 (`4429 too_many_connections`). SysOp is not limited.
- **Engine views.** New connections, resyncs and game reads share one engine view per revision.
- **Game slots.** Games created at the same moment keep to `CD_GAMES_MAX`.
- **Card-image lookups.** At most 8 new names wait on Scryfall per account and 24 in all; more are refused at once (429 `card_images_busy`, or 503), with `Retry-After`. SysOp is never refused.
- **Scryfall's limits.** Lookups are spaced 550 ms apart, as Scryfall's limit for its named-card search allows. After a 429 the API asks nothing for as long as Scryfall says, so the site's address is not banned.
- **Missing card names.** Rows for names Scryfall does not know are deleted after a week, so names sent by clients cannot grow the table for good.

**Hidden information and errors:**
- **The log and the board.** Each seat's log stops at the entries that existed when its view was built, so a line such as "Bot 2 casts …" never reaches the browser before the board shows the spell (plan item 5). The browser leak check is strict again.
- **XMage's error lines.** Its recovery lines, which carried exception text, reach seats as plain notices. A game whose engine thread fails ends with a plain error; the details stay in the engine's log.
- **The engine's replies.** An unexpected failure answers 500 `internal_error` without its details, instead of dropping the connection. Numbers past JSON-number limits are refused like any other bad number.

### Bugs

**Sessions:**
- **A role change no longer signs the player out** (plan item 1), even when the next request fails or parallel requests carry the old cookie. The rotated cookie now rides on error responses, a bug's 500 included, and on routes that return their own response, the card-image routes included. The old token signs requests in for 60 seconds. The card-image routes' own workaround is gone. A 500 now has the API's error shape and request ID instead of Starlette's plain text.
- **Mid-game.** A role change, or an HTTP request that rotated the cookie, closes the game's connection with `session_refresh`. The page renews the session and reconnects instead of saying the player was signed out.

**Sign-in, Profile, Administration and navigation:**
- **The Google challenge** is renewed before its 10 minutes lapse, also after a device slept, but never while a sign-in with it may be under way. Background tabs no longer renew it.
- **Network failures.** Posting Google's token, signing in as SysOp and changing SysOp's password say the service is unavailable instead of hanging. A failed reload of the account keeps the player signed in; only a 401 signs the page out.
- **Before the bootstrap loads,** Profile says sign-in is being prepared, and offers a retry if the service did not answer, instead of saying sign-in is not set up.
- **Sign-out** shows the signed-out screen only when the server confirms it, ignores a double click, and handles another tab having signed the browser in since.
- **Races.** Two first sign-ins of one Google account, two claims of one handle and two grants of one role end in a clear answer, not a server error.
- **A malformed token header** is an ordinary invalid token, not a server error.
- **Admin lists** apply only the newest load. "Show more" pressed twice adds one page. Searching or filtering again reloads and clears a stale error.
- **Focus.** Leaving a game focuses the page's heading, and the skip link no longer leaves the page.

**Wording** (plan item 2):
- The Play page and Settings say practice games against the bots are open for testing; their tags read TESTING PREVIEW. Settings shows which features are available.
- The bootstrap marks practice play available, and `/api/v1/formats` reports Commander and Legacy as available. Only Two-Headed Giant is called planned.
- The engine's `/health` reports `gameplay_available: true` when it serves the API's players' games, and the API passes it through.

**Games through the API:**
- **Closing** a game replies with the game as it ended. A game no task follows any more (left by an earlier process) is marked interrupted and closed in the engine.
- **A short database outage** can no longer leave a game active and its owner blocked. Recording a game's end retries until it lands, and so does the check for games left active at startup, which spares games started since.

**The game screen:**
- **Tapped permanents** take the turned card's footprint and no longer cover their neighbours or the strip beneath them (plan item 3).
- **Answers** name the prompt and revision on screen. A click or a P that lands as a new prompt arrives is refused in the page, never sent as an answer to the new prompt.
- **Focus in the prompt panel** stays on the panel's heading while an answer is sent, and returns to the player's control after a refusal. A card's menu gives focus back to the card, closes on a press outside, and answers in Safari.
- **Amount forms** start from each prompt's own suggestion, and keep what the player typed across a new revision of the same prompt.
- **The lease.** A tab whose connection dropped takes the lease back once the server lets the dead connection go, unless another tab took it. Coming back online never opens a second socket.
- **Too many tabs** are told so, and connect by themselves once a slot frees.
- **SysOp observing** another player's game sees that player named instead of "You", and "Game over" at the end.
- **Card images** that fail for any reason but a missing card are asked for again with backoff, honouring `Retry-After`. A missing card is remembered for an hour, not for the whole visit.

**The engine:**
- **Payments that nothing can finish** (plan item 4). CI run #24's loop is found: Chain Lightning asks the player it hit "Pay {R}{R} to copy the spell?" before XMage checks they can pay. The keyboard journey's player said yes with only Forests, tapped one, then offered the green pool mana 600 times, which XMage takes and asks again. A replay of that table hit it in 11% of games. The payment prompt now offers only sources and pool mana that can pay part of the unpaid cost; with none, it offers only cancel and says "Nothing you control can pay {R}{R}." 1,000 replayed games had no payment loop, and the engine never listed a spell the seat could not pay for. A new test plays that table and checks the copy's payments.
- **Special payments.** XMage counts mana from the hand (Simian Spirit Guide) and its special payments (convoke, delve, improvise) when it lists a spell as castable, but the payment prompt offered neither. The prompt now offers both; a test pays with convoke and with Simian Spirit Guide.
- **Games starting together** on a freshly started engine no longer fail. XMage fills its token list lazily without a lock when a game starts, and two games at once lost one in 2 of 6 fresh starts. The engine fills it once, after loading the card database; 40 games in 5 fresh starts of 8 at once were clean.
- **A seat that concedes before the game starts** is never shown a prompt, and leaves the game at its first request. No new prompt opens while a game is closing.
- **Ending a game whose humans are out.** With one bot left, XMage ends the game and the result is `completed` with that bot as the winner; the engine used to start its own close at the same moment, and the result read `humans_eliminated`. With two or more bots left, the engine still ends the game as `humans_eliminated`, but it now concedes the bots only while a player holds priority or a choice, and stops once the game is over. XMage refused concessions sent between steps or after the end ("Non-game thread can't concede or end games").

**The live site's kit:**
- **The web container** follows a recreated API container: its nginx asks Docker's DNS again every 10 seconds.
- **`deploy.sh`** migrates before replacing anything, so failed migrations leave the running version serving. A tag that does not start falls back to the previous one, only when the database still allows it, and never migrates a restored database forward.
- **`restore.sh`** (new) restores a dump into an emptied database in one transaction, after keeping a `pre-restore` dump, and holds the dump open while old dumps are pruned.
- **Backups** keep separate pools: 14 nightly, 10 pre-deploy and 5 pre-restore dumps.
- **Capacity.** The live site runs up to six games at once instead of two (`CD_GAMES_MAX`, which the engine's slots now follow), with a 3 GB engine heap and a 4 GB limit. The VM's `.env` says `CD_GAMES_MAX=6` from this version.

**Contracts and checks:**
- `EngineStatus.gameplay_available` is a boolean (it was always false). The seat-view contract's options gain `special_payment`.
- The OpenAPI document names 422 itself, so it regenerates the same on Python 3.12 and 3.13.
- **CI keeps the evidence of a failed browser journey** (plan item 6): Playwright keeps a screenshot and a trace on failure, and both jobs that run journeys upload `web/test-results` as an artifact for 14 days. A failed game's error lists the test player's last answers.
- CI checks the deploy scripts with ShellCheck. `tests/test_deploy_kit.py` and `tests/test_sessions.py` are new, and the web client has Vitest tests for the fixes above. The scripted API game checks that inspection views reach only the tab that asked.

**Tidying** (plan item 8): the unused `web/public/brand/logo.webp` is gone, and `scripts/brand_assets.py` no longer makes it.

**Live operations** (plan item 7):
- **The first nightly backup** ran on 2026-10-20 at 04:41 on the VM: a 36 KB dump, exit 0.
- **A restore rehearsal** on the VM, on 2026-10-20: v0.1.1's `restore.sh` restored that nightly dump into a scratch Compose project (its own database, stand-ins for the API and the worker), never the live one. It took 13 seconds and named the dump's last migration, `0004_card_images`, and the stand-ins stayed stopped. Every table matched the live database, except sessions, audit events and sign-in challenges, which had grown from sign-ins since 04:41. The project was then removed.
- **Off the VM.** The owner backs up the whole VM to the NAS with Proxmox VE's scheduled backups. Every VM backup carries the consistent dumps in `backups/`.
- **The phone check** from mobile data is recorded with the live checks at the deploy of `0.1.1`.
