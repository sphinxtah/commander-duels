# v0.9.11: a game's start

Opened and closed on 2026-11-12, the day v0.9.10 reached the live site. One fix, asked for by the owner's first report on v0.9.10: a game took 30 to 35 seconds to load. Once dealt, it played smoother than ever, past forty turns. The stage staged as v0.9.11 (the economy, the deck workshop, Rule Zero profiles, playgroups and leagues, large boards, rollout and operations) is now [v0.9.12](../plans/0.9.12.md); each version is one thread of work, and this one could not wait for that one.

## What was slow, and why

Measured through the owner's browser on the live site (v0.9.10, a practice table against three bots): the create took 13.0 s, and the table's first state came 16.1 s after it, 29.2 s in all. Lined up with the owner's Proxmox graphs, the loads at 20:52 and 21:15 show no disk, CPU or memory pressure; the burst of disk traffic at 20:45 was the upgrade itself (the images, the migrations, the engine's start and its warm-ups). A game's start is one thread's work, and the VM's cores (two Xeon E5-2687W v3, from 2014) take about three times as long at it as the cloud workspace's. In the workspace the same table took 8.6 to 10.5 s, so three causes were found and measured there:

- **The cards were read through another process.** Every game process looked up each card of each deck in the front process's card database, over loopback, one query at a time: 4 to 5 s of a four-deck table's start.
- **Every game paid a fresh Java process.** XMage's game, rules and AI code was loaded and compiled again for each game. Before v0.9.10, every game after the engine's first found it ready (0.4 s to a table's first question).
- **The warm-up played the wrong decks.** A process's warm-up game used the engine's small fixture decks, so a player's own cards and the bots' starter decks were still cold.

## What changed

- **Each game process opens its own copy of the card database** ([the card database](../engine/isolation.md#the-card-database)). The front process copies the file into the container's temporary folder before it opens it (75 MB, once per engine build), and each game process opens the copy read-only, with no server: its lookups stay in its process. XMage patch 0020 gains that option.
- **A process plays the next game of its size** ([one process, many games](../engine/isolation.md#one-process-many-games-v0911)). Thirty seconds after its game is over, the process drops the game, whose end is in its recording, and goes back among the warm processes, the first to be taken. It is ended instead after 40 games (`CD_ENGINE_GAME_REUSE`), after 24 hours, or when its heap stays half full after a collection. Two games never share a process, and nothing of one reaches the next: each has its own random generator, seats, recording and events. Twelve tables played one after another in one process held their threads and memory flat.
- **A process warms up with the decks of a recent game of its size**, read from the newest recordings' manifests, played by no one and shown to no one; the fixture decks when there is none.
- **The engine's log loses an error at every game's start.** The events' tap asked XMage whether it was already attached, and XMage logs every such question it cannot answer as an error with a stack trace. It is now attached the way XMage keeps the first one.

A four-deck Commander table's first question after its create, on the workspace's two cores:

| | First question |
| --- | --- |
| v0.9.10 | 8.6 to 10.5 s |
| v0.9.11, a process's first game | 2.5 s |
| v0.9.11, a process that has played a game | 0.5 to 1.3 s |

On the live VM, about three times these: some 7 s for the first game of a fresh process, 2 to 4 s for the games after it, against 29 s. **Watch after deploying:** the time from "start" to a dealt table, and in `GET /v1/service/processes` the new `reused`, `games_per_process`, each warm process's `warm_games` and each game's `games_in_process`.

## Verification

- **Engine:** `GameProcessesTest` (its five tests, the new one with them: a process whose game is over takes the next game, the first answered from its recording and never taken up again, and is ended once it has played its share), `GameEventsTest`, `ServiceRecoveryHttpTest` and `EngineServerTest` in the workspace, all passed; the whole suite in the hosted checks.
- **Measured** in the workspace with the campaign's decks: the table above; twelve tables in one process at 0.45 to 0.78 s each, 30 threads throughout, 480 MB resident from the seventh on, the old generation at 1% of its heap.
- **API:** `ruff` clean; the contract, access and version tests passed (117), contracts regenerated for 0.9.11.

## Upgrading

- **No migration.**
- **The engine image must be rebuilt**, the private one too: XMage patch 0020 changed, and the engine's code.
- **Nothing in `.env` has to change.** `CD_ENGINE_GAME_REUSE` (40) sets how many games a process plays; 1 restores v0.9.10's one game a process.
- **Games running at this upgrade end interrupted**, as at every upgrade: a recording is played on only by the engine build that made it.
