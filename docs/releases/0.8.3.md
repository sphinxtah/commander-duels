# v0.8.3: the bug hunt's fixes

A patch version, opened and closed on 2026-11-01. The next version is v0.8.4 ([the plan](../plans/0.8.4.md), carried from v0.8.0's close).

## Scope agreed for this version

The owner, 2026-11-01, had v0.8.2 searched for bugs (the API, the engine, the web app and the deploy kit, read side by side), then: "Go ahead an implement all of the recommended fixes for the 12 bugs you found." And: "When you're finished, we'll call this v0.8.3, you can close the version and push to Github." The search's report, with its lesser findings left for later, is the owner's and stays out of this public repository.

## Fixed

### The API

- **Deck lists are read in time proportional to their length.** A deck import's text and SysOp's typed deck lists read runs of spaces and tabs as one space, and refuse a line longer than 300 characters, before any pattern reads it. The patterns took time growing with the square of a long run of spaces, and the API is one process, so a single crafted import could hold up every page and game for close to a minute. An import also looks up suggestions for its first 40 unknown lines only ([decks](../decks.md)).
- **Learn Commander is the first ward's alone.** Its disclosed training seed fixes the shuffles, and the API took it on any ward: a player who lost a later duel once in Learn Commander would know both decks' order for the replay, The Sphinx's included. Any other ward now answers `422 invalid_seat` ([the campaign](../campaign.md#a-duel)).
- **Alliance messages and votes have limits.** At a table, offers, answers and votes on an away player were not counted against chat's limits, and each is said to every connection there, so a loop of them could flood the table. They now have limits of their own, 12 in 5 seconds and 60 a minute, and an offer made again while it stands is said to nobody ([chat](../chat.md)).
- **A game whose end cannot be recorded no longer stays active.** Writing a game's end was retried on any database error, forever, and any other error lost it: either way the game stayed `active`, its players could start no other game, and Close could not clear it. Now only an unreachable database is waited for; any other failure is logged and the game recorded `interrupted`, and if even that fails, the game alone is marked `interrupted`. Following a game that fails beyond recovery ends it the same way, a view without its revision is retried as an unreachable engine is, and a failed task is logged when it fails ([games](../games.md)).
- **Creating a game in the engine is safe to retry.** The API names each game it asks the engine for and waits 30 seconds (it waited 10). When no answer comes, it closes that id, which also stops a create that reaches the engine later, so no game is left holding an engine slot with nothing following it; a best-of-three match's next game, which retries on its own, can no longer fill the engine that way.

### The engine

- **A card put face down is no longer named.** A card revealed or looked at and then foretold, exiled face down, turned face down or cast face down stayed in XMage's revealed lists, and the seats' and spectators' views named it from there. The lists now count only for a card in a hand, a library or outside the game; a face-down permanent or spell is its controller's to see, and a face-down exiled card nobody's ([the human seat](../engine/human-seat.md)).
- **Bots no longer see face-down cards.** The fair bots' search re-dealt hands and libraries but kept the real card behind an opponent's face-down cards, which mattered once players brought their own decks. A face-down exiled card is now dealt from that opponent's unknown cards in the search, and an opponent's face-down permanent or spell cannot be turned face up in it ([fair bots](../engine/fair-bots.md#face-down-cards-v083)).
- **A service create may name its game.** `game_id` on `POST /v1/service/games` is the game's id; an id in use answers `409 game_exists`, a cancelled one `409 game_cancelled`, and a close of an id with no game cancels it for 15 minutes. Without `game_id` nothing changes.

### The web app

- **P answers one prompt per press.** A held P repeated, and each repeat answered the next prompt as it appeared: passing, keeping a hand or saying yes to a trigger the player never saw. Repeats are now ignored ([the game screen](../game-screen.md)).
- **The deck editor no longer conflicts with itself.** An edit made while a save was out was sent with the version that save was replacing, and the server called it an edit from another tab. Saves now run one after another, each with the version the last returned. Leaving the editor for another page sends an edit not yet saved (or whose save failed) instead of dropping it, a page closed after a failed save asks first, and "Save version" saves the draft first and stops if that fails ([decks](../decks.md)).

### The deploy kit

- **The database is dumped before every migration.** `deploy.sh` decided whether there was a database to back up by whether its container was running, so after `docker compose stop` a deploy migrated live data with no dump. It now starts the database first, dumps it whenever it holds any table, and stops with nothing replaced if the database will not start or the dump fails ([the live site](../deployment.md)).
- **One deploy kit per version.** `upgrade.sh`, `update.sh` and `push.sh` replaced the folder's `compose.yaml` and scripts before anything was pulled, so a fall-back ran the old images under the new kit, and `push.sh` shipped the checkout's working tree. Each version's kit now lives in `/srv/commander-duels/kits/<version>/`: a deploy runs with its own, a fall-back or rollback with the previous one's, and only a successful deploy makes its kit the folder's own. `push.sh` ships the tag's committed kit and checks the tag before connecting ([the live site](../deployment.md#one-kit-per-version-since-v083)).

## Deploying 0.8.3

No migration and no `.env` change. The private images must exist at the tag first (the private repository's engine and web workflows, run once the tag's run has published the public `0.8.3` images). Then, on the VM, as always: `cd ~/commander-duels && git pull && bash deploy/upgrade.sh`. This first deploy with kits saves the running 0.8.2's files as `kits/0.8.2/` before anything changes, so its fall-back still works; nothing needs doing by hand. Deploy soon after the tag: the fixes, public from the push, describe what they fix.
