# v0.0.3: human seat and per-seat views

Second slice of milestone M0. A human seat plays a Legacy Two Player Duel against an XMage computer player through XMage's own `HumanPlayer`. Every blocking choice becomes a typed prompt with an ID, stale answers are refused, and the seat receives only an authorized view. Gameplay stays unavailable to players: these are development games driven by scripts, there is no game UI, and the FastAPI application still refuses game actions. Design and findings are in [the human seat](../engine/human-seat.md).

## Scope agreed for this version

- **Proof:** JUnit tests and a scripted client play complete human-versus-bot Legacy games and check every payload sent to the human seat for concealed information. A one-line development command plays a scripted game and prints the prompt and answer transcript. No UI, so this stays a 0.0.x version.
- **Boundary:** internal, development-gated engine endpoints, like `/v1/bot_match`. FastAPI keeps refusing game actions until sign-in, seat ownership and controller leases exist.
- **Prompts:** every prompt family the two fixture decks reach is typed and tested. Any other family pauses the game with a typed `unsupported` prompt instead of guessing.
- **Not included:** the AI hidden-information audit (AI02). The bot opponent still searches a full copy of the game state, including the human's hand.

## Included

- **XMage human player:**
  - The engine image now also builds `Mage.Player.Human` from the pinned commit (`xmage_1.4.62V1`, no patches); the XMage compile went from 167 s to 177 s locally.
  - The human seat is XMage's unmodified `HumanPlayer`, with XMage's default user settings.
- **Prompt bridge:**
  - A listener on XMage's `PlayerQueryEvent`s turns each request into a typed prompt with a fresh ID, published with the seat's view at a new revision, on the game thread.
  - Kinds: `priority`, `mulligan`, `yes_no`, `choose_target`, `pay_mana`, `declare_attackers`, `declare_blockers` and `assign_amounts` (damage split among blockers, found reachable with the fixture decks), plus `unsupported`.
  - Answers name the open prompt, the current revision and one option ID, or a list of amounts for a split.
  - Refusals: `stale_prompt`, `stale_revision`, `invalid_option`, `invalid_amounts`, `unsupported_prompt` and `game_over`. A repeated action ID returns its first result; a reused one with a different body is refused.
- **Authorized views:**
  - Built field by field: your hand; the battlefield, stack, graveyards and face-up exile; revealed and looked-at cards while XMage keeps them; players' life, counters, mana pools and hand and library counts; combat; personal messages.
  - Object IDs are opaque and change when an object changes zones.
  - The views never show XMage UUIDs, either library, the opponent's hand, sideboards or the seed.
  - XMage's own client view would show a computer opponent's sideboard; this one does not.
  - The public log drops XMage's short object IDs and engine error lines.
- **Development endpoints** (with `CD_ENGINE_DEV_ENDPOINTS=true`):
  - `POST /v1/games` returns a seat token once.
  - Under `/v1/games/{id}`: `GET .../view` (long-polling, log paging), `POST .../commands` (`submit_choice`, `concede`) and `POST .../close`.
  - The bearer token alone selects the seat. Unknown games and wrong tokens both return 404.
  - At most `CD_ENGINE_MAX_GAMES` games run at once (default 2), and a watchdog closes idle games (default 15 minutes).
  - Finished games stay readable for 10 minutes.
- **Contracts:**
  - The command envelope gains `concede` and typed `submit_choice` payloads.
  - The new `contracts/engine-seat-view.schema.json` closes every object, so a payload cannot carry an opponent's hand, library contents, the seed or XMage identifiers.
  - Python contract tests prove both.
- **Tools:** `scripts/engine_human_game.py` plays a scripted game through the HTTP endpoints and prints it. It checks every payload, validates against the seat-view contract with `--schema`, and verifies stale-answer refusals.
- **Tests and CI:**
  - 45 JUnit tests, up from 29. They include six complete scripted games with leak checks on every published view; concede, close, idle timeout and the game cap; HTTP boundary tests; and parser tests.
  - The CI engine job adds a schema-checked human-seat game after the bot match.
- **Docs:** the human seat, architecture, backlog (now including the SysOp local administrator requirement), README, dependency ledger, and [the plan for v0.0.4](../plans/0.0.4.md).

## Not included

- A browser interface, sign-in, seat ownership, and API routing of game actions.
- Four-seat Commander and Two-Headed Giant. XMage has no Two-Headed Giant game type at the pinned commit.
- Prompt families the fixture decks never reach.
- Timers and configurable stops.
- Journals, recovery and reconnect.
- The AI hidden-information audit.
- Scryfall import and the TeaVM probe.

Gameplay remains unavailable to players.
