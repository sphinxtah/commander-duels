# v0.7.3: the menu playlist

A patch version, opened and closed on 2026-10-31 (tag `v0.7.3`). The owner opened it for the menu playlist planned since v0.7.2 ([the v0.7.3 plan](../plans/0.7.3.md#scope-agreed-for-this-version-2026-10-31)) and asked for the close, the commit and the push in the same breath. The next version is v0.8.0, the Campaign.

## Scope agreed for this version

The owner, 2026-10-31: "Lets do v0.7.3 now, the menu music playlist. I want a hovering box in the corner of the screen that allows you to control which song is playing and the ability to uncheck songs you don't like so it skips them. It should also allow shuffle play or in order play. It should also allow music volume or music muting. The 20 songs are in the music folder." And: "the music playlist plays everywhere in the app except for during gameplay, which has it's own separate music track." The decisions taken are in the plan: the box in the lower left corner, folded to a pill; the manifest beside the songs; the playlist's own volume and mute; the last ticked song staying; a paused player staying paused; track 20's ASCII file name; plain git for the songs.

## Added

- **The music box** ([menus](../menus.md#the-music-v073)). On every page of the signed-in app a small player is fixed in the lower left corner of the window. Folded, it is a pill with the song's name and Play or Pause; open, it shows the song playing (its title and artist, as a live status), Previous and Next, **Shuffle** or **In order**, the volume (0–100, 50 by default, the level (volume/100)²) and its mute, and the list of the playlist's songs, each with a tick: an unticked song is skipped, the last ticked one cannot be unticked, and a song clicked in the list plays at once whatever its tick, the ticked songs going on after it. Shuffle plays each ticked song once before any repeats and never opens a round on the song just heard; In order goes down the list and round again; Previous walks back through what was heard. The songs stream as they play (`preload="none"`, Range requests); a mute or a pause streams nothing. The browser's rule holds: a visit that opens on a page waits for the first click or key press, and the box says so.
- **Hand-off with the game.** The game screen replaces the whole shell, so the box unmounts as a game opens: the song fades out over 0.8 s and holds its place while the game's own track plays ([the game screen](../game-screen.md#the-table)); back from the table, it fades in over 1.2 s from the same second. A sign-out fades it out the same way, and a sign-in starts it again.
- **Settings › Menu music**: the volume, the mute and Shuffle, among the other sound settings. **Mute all sound** (Settings › The table) silences the playlist too, and the box says "All sound is muted in Settings". The game track's own volume and mute are unchanged. The box's settings (`cd.menuMusic.v1`: volume, mute, order, the ticks, open or folded, paused by hand, the song playing) stay on the device; the next visit begins with the same song, and a player paused by hand stays paused until Play.
- **The manifest.** Which songs there are is `/music/playlist.json`'s business, `{"tracks": [{"file", "title", "artist"}, …]}` in the order they play in, read afresh on every visit (`cache: "no-cache"`) from the same folder as the files. The owner's twenty songs and the manifest are in the private repository's `music/` folder beside `game.mp3`, plain git (100 MB in all, the largest file 7 MB), and the private web image serves them under `/music/` as it does the track; its smoke test now checks the manifest and every song it names ([the live site](../deployment.md#the-web-image-with-the-music-v072)). Locally the gitignored `music/` folder beside `compose.yaml` holds the same files and manifest, mounted into the web container and served by the dev and preview servers (`web/plugins/music.ts`, which serves plain ASCII file names only: track 20's file is `…-Lumiere.mp3`, its title Lumière). The public images have no manifest: the request answers 404 and no player is drawn. A manifest that names a missing file costs one failed request a visit, after which the song is skipped; when every song fails the box goes away.

## Changed

- **Settings › The table › Music volume** no longer says the menus have no music; it points to the playlist below.
- `docs/menus.md`, `docs/game-screen.md`, `docs/deployment.md`, the README, `compose.yaml`, `.gitignore`, `.dockerignore` and the deploy kit's comments name the playlist beside the gameplay track.

## Not changed

- The API, its contracts (the version only), the migrations, the engine and the worker. The playlist is the browser's: one `<audio>` element, a JSON file and nginx serving static files. No API route, WebSocket frame or engine message changed.
- The gameplay music (`web/src/game/music/`): its player, settings and hand-off are as v0.7.2 left them; the menu playlist is a second player (`web/src/shell/music/`) that only reads the table's **Mute all sound**.
- The menus' generated sounds (`web/src/shell/menuSound.ts`).
- The service worker: `/music/` was already passed through to the network, the manifest with it.

## Deploying 0.7.3

No migration and no `.env` change: `CD_WEB_IMAGE` from v0.7.2 names the private web image already. `deploy.sh` pulls both private images at the tag, so `commander-duels-engine-sphinx:0.7.3` and `commander-duels-web-sphinx:0.7.3` must exist first: the private repository's two workflows, run (or scheduled) once the tag's run has published the public `0.7.3` images. The private repository's push of the songs (2752b7e) built `commander-duels-web-sphinx:0.7.2` with the playlist in it, harmlessly: v0.7.2's menus never ask for the manifest. Then, on the VM: `cd ~/commander-duels && git pull && bash deploy/upgrade.sh`. The owner hears the playlist in the local Docker stack first (`docker compose up --build` with `music/playlist.json` and the songs beside `game.mp3`).
