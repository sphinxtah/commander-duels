# v0.0.5: identity — sign-in, sessions, roles and SysOp

The identity foundation on the route to v0.1.0. Players sign in with Google and get a private account with a handle, an avatar and their accessibility preferences. Administrators approve accounts, assign roles and read an append-only audit trail. SysOp, the local root account modelled on Kingdom Connect's, signs in with a password, and only from the operator's network. Games still run only on the engine's development endpoints: the API routes no game actions, and gameplay remains unavailable to players. Design and decisions are in [identity](../identity.md).

## Scope agreed for this version

Agreed on 2026-10-18:
- **Google sign-in:** the full flow, with open sign-up. Approval mode is a setting (`CD_SIGNUP_POLICY=approval`).
- **SysOp:** Kingdom Connect's design, without a second factor.
- **SysOp's powers:** everything, with no exceptions. It sees concealed information in live games (an accepted exception to SEC05 and NET14, for SysOp only), plays against bots to test them, and can add any card in the card database to its own library to test combinations. The last two were added mid-thread.
- **Screens:** sign-in, profile and administration in the browser. There is no game screen, so this stays a 0.0.x version.

## Included

- **Google sign-in (AUTH01–AUTH05):**
  - Google Identity Services' ID-token flow with a JavaScript callback. Each attempt starts with a server challenge: the nonce goes into Google's signed token, and the browser keeps the matching secret in an HttpOnly cookie.
  - The token is verified with Google's `google-auth` library: signature against Google's cached certificates, audience, issuer and expiry. The nonce must match the cookie, and the challenge is consumed, so a stolen or replayed token opens nothing.
  - Accounts are keyed by issuer and Google subject, never email; a changed email updates the private record without a second account.
  - New players choose a unique handle (3–20 characters; names such as `sysop` reserved) and one of eight built-in avatars.
  - Email and the Google subject stay private. The subject is never returned.
- **Sessions (AUTH03):**
  - A random token in a Secure, HttpOnly, SameSite=Lax cookie; the database stores its hash.
  - Players: 14 days idle, 30 days absolute. SysOp: 60 minutes and 12 hours.
  - New identifiers on every sign-in and after any role or status change.
  - Sign out, sign out everywhere, and a list of active sessions with per-session sign-out.
  - Role and status changes need a sign-in under 12 hours old.
  - CSRF: every state-changing request carries the session's token in a header. Requests from another origin are refused before any session is read.
- **Roles and administration (AUTH06, SEC05):**
  - Player, moderator, content editor and administrator, with least-privilege permissions checked on the server.
  - Administrators approve and deny pending accounts, disable and restore accounts, sign accounts out everywhere and grant the moderator and content-editor roles.
  - Only SysOp makes or removes administrators. SysOp is AUTH06's configured bootstrap: no Google account becomes an administrator by signing in.
- **SysOp:**
  - The fixed username `sysop` and its own entrance (`#sysop`), which exists only for `CD_SYSOP_NETWORKS`. Elsewhere it is indistinguishable from an unknown address, and its routes are not in the published API document.
  - An Argon2id password, at least 12 characters, set from the console with `python -m api.cli sysop-password` (interactive, `--stdin` or `--password-file`). It can be changed in the Profile page. Setting or changing it ends every SysOp session.
  - Five failures from one address in 15 minutes lock that address out.
  - SysOp sessions stop working off the network.
  - `X-Forwarded-For` is believed only from `CD_TRUSTED_PROXIES`, and a SysOp network may not contain a trusted proxy.
  - SysOp holds every permission, including three no role can be granted: making administrators, seeing concealed game information, and using any card. The last two take effect with game routing and deck lists.
  - SysOp never appears in account lists. Other audit viewers see it as *Site administrator*, without its addresses or its sign-in trail.
- **Audit trail:**
  - Every sign-in, failure, sign-out, profile change, SysOp password change and administrative action, with its source address and request ID.
  - PostgreSQL refuses updates and deletes on the table.
- **Browser:**
  - Profile: Google sign-in, the handle choice, the profile form, active sessions, sign-out; for SysOp, the password change.
  - Administration (visible only with the permission): accounts with filters, search, approval, roles and status; and the audit log.
  - The SysOp sign-in page.
  - The sidebar shows the signed-in account.
  - Accessibility preferences follow a signed-in account across devices.
  - A signed-out visitor to Administration is offered sign-in and brought back afterwards.
- **Data:**
  - Migration `0002_identity`: profile columns, `sessions`, `role_grants`, `audit_events`, `login_challenges`, the one-SysOp index and the append-only trigger.
  - New dependencies: `argon2-cffi` 25.1.0 and `google-auth` 2.62.0, with their locked transitive packages.
- **Infrastructure:**
  - The web container's Content Security Policy allows Google's sign-in script, stylesheet and button frame. Referrer-Policy is now `strict-origin-when-cross-origin`, as Google requires.
  - The proxy forwards `X-Forwarded-For`.
  - Fixed while here: `index.html` had been served without the security headers, because its location block declared its own `add_header`.
  - Compose gives its network a fixed subnet: the web container is the trusted proxy, and the gateway (this computer) is the development SysOp network.
  - Uvicorn runs with `--no-proxy-headers`.

## Not included

- Routing games through the API, seat ownership and controller leases (v0.0.6), and with them SysOp's practice games, its inspection view and its any-card test decks.
- Signing in from the installed PWA (M5). Account deletion and data export. Moderation reports and content publishing: the roles exist, their tools do not.
- A second factor for SysOp, by decision.

Gameplay remains unavailable to players.

**Live checks, 2026-10-19.** Run in Compose on this computer, with a real Google account:
- **SysOp.**
  - Its password was set with `docker compose exec api python -m api.cli sysop-password`, which created the account.
  - SysOp signed in at `#sysop` from this computer's browser, and again later from the desktop app's browser pane.
- **Google.**
  - A Google Cloud project "Commander Duels" with a Web client (origins `http://localhost` and `http://localhost:8080`), in Testing with the owner as test user.
  - The client ID went in the git-ignored `.env`.
  - Sign-in with the owner's Google account created one active player linked to one Google identity. The account chose its handle and avatar, signed out and signed in again.
- **Administration.** SysOp granted Moderator, removed it, then granted Administrator. The administrator's next request rotated its session, as designed.
- **The audit trail** recorded each of those steps, from the Docker gateway address that stands for this computer:
  - SysOp's console password and sign-ins;
  - the Google sign-up and sign-ins;
  - the two profile updates and the sign-out;
  - the role grants and the removal.
- **One console note.** The Content Security Policy blocks three inline styles that Google's script tries to add (a `<style>` element and two style attributes). The button, its frame and the sign-in all work, so the policy stays strict.
