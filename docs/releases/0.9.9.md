## Changed without asking

**Isolation and the structured events moved to v0.9.10.** They were to be built beside recovery. A game moved into a process of its own needs its whole state to cross into that process, and the recording is that state; the events are written beside the recording and name objects by the ids it keeps stable. Building them on a finished recovery is the safer order, and recovery took the version. What v0.9.9 has in their place: an engine that runs out of memory exits and is restarted by Docker, and every game it ran is taken up again from its recording; a game that keeps killing the engine is given up after five recoveries with no answer between them. One game's memory still cannot be bounded on its own, and while the engine restarts every game waits a few seconds. [The audit](../plans/audit-0.9.9.md#how-the-work-is-staged) has the stages; if v0.9.11 cannot close its six foundations, a v0.9.12 takes the rest, which is the owner's call when v0.9.10 closes.

## The pack window

Opening a pack shows its cards in a window over Leng's shop, as the owner asked. Only the window's body scrolls (the pack, its cards, the summary); its title and buttons hold still, and the shop under it is locked, by the wheel, by touch and by the keyboard alike, and is where it was when the window closes. Space turns the next card and brings it into view. A close button and Escape work at every stage: the cards are the player's before any of it. A warden's deck in the campaign opens in the same window, in place of its own pop-up, which scrolled its title and buttons away ([the shop](../shop.md), [the campaign](../campaign.md)). Tested in Chromium at a desktop's, a phone's and a phone's turned size with a 75-card Tournament Pack: nothing but the cards moves.

## Games that survive a restart

Every game played through the site keeps a recording of itself in the engine: the decisions every seat makes, written to disk before they are acted on, and the whole state of the game, written each time a person is asked something. When the engine stops (it ran out of memory, it was restarted, the VM rebooted), the API asks for each running game again and the engine takes it up from its recording, where it stood. When the API restarts, it asks the engine for each game it was following. The players' tabs reconnect by themselves and play on. Before this version both restarts ended every running game as interrupted. [Recording and recovery](../engine/recovery.md) says how it works, what it costs and what it does not cover.

- **Each seat sees what it saw.** In the tests real games in every format were stopped as a dead process stops, in the middle of whatever they were doing (spells on the stack, attackers and blockers, a payment half made, mulligans, teams, commanders), 587 times in one run, and taken up again; every seat's view, question, log, hand and library was compared with before. A game built with an extra step, two extra phases and an extra turn, stopped before each of its 134 answers, ends with the same log line for line as the game played straight through.
- **Nothing is done twice.** An answer sent again after a recovery is answered as it was; a concession stays one; a game that ended while the API was down is recorded once, with its win, pay and rewards.
- **Bad data fails safely.** A damaged checkpoint is passed over for the one before it and said so in words; a recording that cannot give back the game that was played gives back none, and that game ends interrupted, as before.
- **An upgrade still ends running games.** A recording is played on only by the engine build that made it, and every release builds a new engine.
- **Costs.** A few milliseconds of the game's own time at each priority, under 1 MiB on disk for a running game, and 0.1 to 0.4 seconds to take a game up.
- **For the operator.** `GET /v1/service/recordings` gives the numbers, and `RecordingTool` says whether each recording is whole without showing anything of a game ([deployment](../deployment.md#recordings-v099)).

**XMage patches 0018 and 0019.** XMage could resume a game only at the start of a phase, and some of its saved objects could not run again; 0018 resumes a saved game exactly where it stood, extra steps, phases and turns included. Writing every card once found 37 of 33,612 whose state Java could not write; 0019 makes them writable. Neither changes how any game plays ([the patches](../../engine/xmage/patches/README.md)).

**Found while building it**, each fixed: XMage's copy of a player kept the table's own players and a bot its search tree, which made a Commander checkpoint four times its size and could fail while the game changed them; an ability gained from an effect has a new id each time effects apply, so the journal names such a choice by its object and its words; a game's result was told to the seats before the recording had it; a concession XMage had not yet applied was lost; a recording that had stopped (a full disk) would have been played on from wherever it stopped, turns behind its game, and is now refused; an answer asked for a state that was already being written, so the next one was written twice.

**The owner's private cards** were played once against this engine with recording on, outside the public repository: their nine scripted games wrote 473 checkpoints, 485 were read back at the questions asked, and no state was skipped.

## Upgrading

- **No migration.** The previous version reads nothing new, and rolling back to v0.9.8 needs no restore.
- **The engine image must be rebuilt**, the private one too: XMage patches 0018 and 0019 and the recorder are the engine's.
- **A new volume**, `engine_recordings`, created by the deploy. Two optional settings, with their defaults in the Compose file: `CD_ENGINE_RECORDING_RETENTION_HOURS` (24) and `CD_ENGINE_CHECKPOINT_SECONDS` (3). Nothing in `.env` changes.
- **Games running at this upgrade end interrupted**, as at every upgrade: they were not recorded, and the next upgrade's will be another build's. From this version on, a restart that is not an upgrade no longer ends them.
